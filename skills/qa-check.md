# Skill: qa-check

The pre-merge QA ritual. Run this AFTER `npm run build` passes and BEFORE
merging any feature branch into `develop` (skills/release-manager.md §3).
It catches the mistakes a green build alone does not: broken structured
data, stray emoji, and visual regressions.

## 1. Build must be green first

```bash
npm run build
```
Expect `Result (N files): 0 errors`. If this fails, stop and go to
`skills/troubleshoot-build.md` — nothing below matters until this passes.

## 2. JSON-LD parse loop (every structured-data block must be valid JSON)

```bash
python3 -c "
import re, glob, json
fails = 0
for f in glob.glob('dist/**/*.html', recursive=True):
    html = open(f, encoding='utf-8').read()
    for m in re.findall(r'<script type=\"application/ld\+json\">(.*?)</script>', html, re.S):
        try:
            json.loads(m)
        except Exception as e:
            fails += 1
            print('FAIL', f, e)
print('JSON-LD blocks checked, failures:', fails)
"
```
Expect `failures: 0`. Astro almost never breaks this on its own — a
failure here nearly always means a hand-edited `jsonLd={[...]}` prop in a
`.astro` page produced a JS object that doesn't serialize cleanly (rare).
If you see a failure, open the file it names and re-check the `jsonLd`
prop passed to `<Layout>`.

## 3. Emoji grep (rendered UI must stay emoji-free — AGENTS.md golden rule #7)

```bash
python3 -c "
import re, glob
EMOJI = re.compile(r'[\U0001F300-\U0001FAFF\U00002600-\U000027BF\U0001F1E6-\U0001F1FF]')
hits = 0
for f in glob.glob('dist/**/*.html', recursive=True):
    html = open(f, encoding='utf-8').read()
    for m in EMOJI.finditer(html):
        hits += 1
        print(f, repr(m.group()))
print('emoji hits:', hits)
"
```
Expect `emoji hits: 0`. The `©` character is not an emoji and is fine in
the footer copyright line. `menu.json` itself is ALLOWED to keep emoji in
its raw text (it mirrors the Zomato catalogue) — `src/lib/data.ts`
(`displayName`/`displayDescription`) strips them at render time, so a hit
here means something bypassed those helpers, not that `menu.json` needs
editing.

## 4. Honesty checks (no fabricated rating, no non-veg wording)

```bash
grep -rn "ratingValue\|reviewCount" dist/*.html dist/**/*.html 2>/dev/null | sort -u
```
Every line must show the SAME numbers as `site.config.json` → `rating`.
Any other number is a hard stop — see `skills/update-rating.md`'s honesty
warning.

```bash
grep -rli "chicken\|mutton\|prawn\|keema" dist/*.html dist/**/*.html 2>/dev/null
```
Expect no output. The kitchen is 100% pure veg (AGENTS.md golden rule #6)
— any hit here is a content bug, find where the word came from (usually
`menu.json` description text) and fix it.

## 5. Dist spot-checks (titles, descriptions, images)

```bash
python3 -c "
import re, glob
for f in sorted(glob.glob('dist/**/*.html', recursive=True)):
    html = open(f, encoding='utf-8').read()
    title = re.search(r'<title>(.*?)</title>', html)
    desc = re.search(r'<meta name=\"description\" content=\"(.*?)\"', html)
    imgs_no_alt = len(re.findall(r'<img(?![^>]*\balt=)[^>]*>', html))
    t = title.group(1) if title else 'MISSING'
    d = desc.group(1) if desc else 'MISSING'
    print(f'{f}\n  title ({len(t)} chars): {t}\n  desc ({len(d)} chars): {d[:60]}...\n  <img> missing alt: {imgs_no_alt}')
"
```
Look for: every page has a title (≤ 60 chars is ideal, not a hard rule),
every page has a description (≤ 155 chars ideal), and `<img> missing alt`
is `0` everywhere.

## 6. When to also run the parity/screenshot suite

The full visual-parity screenshot pass (Playwright at 390/768/1440px,
described in PROGRESS.md's Phase 3 entry) is NOT part of routine QA — it
is expensive and was a one-time migration acceptance test. Only re-run
something like it when:
- you touched `src/layouts/Layout.astro`, `src/components/Nav.astro`,
  `src/components/Footer.astro`, or `src/styles/global.css` /
  `src/styles/polish.css` (shared chrome — a mistake here shows on every
  page), or
- Milan asks for a visual review before merging a copy/design change
  (owner approval gate, `skills/release-manager.md` §3).

For a routine content edit (price, description, photo, new blog post),
steps 1–5 above are sufficient — do not spend time on a screenshot pass
for those.

## 7. If anything in this checklist fails

- Build itself fails → `skills/troubleshoot-build.md`.
- Everything else (steps 2–5) → the fix is almost always in the file the
  failure names (`menu.json`, `site.config.json`, or the one `.astro`
  page listed) — re-open the matching edit skill (e.g.
  `skills/update-rating.md`) rather than patching `dist/` directly. Never
  hand-edit anything under `dist/` — it is entirely regenerated by
  `npm run build` and any hand edit is silently lost.

## 8. This is part of every merge, not a separate step

Run this AFTER `npm run build` passes on your feature branch and BEFORE
`git merge --no-ff` into `develop` (skills/release-manager.md §5) — and
again after the merge, on the merged `develop` state, since a merge can
combine two individually-fine branches into a broken one.
